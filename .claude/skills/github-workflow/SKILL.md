# GitHub 作業フロー

このスキルは、GitHub 関連の作業を AI 間で共用できる形に保つために使う。
特定のプラグイン、拡張機能、チャット製品に依存したワークフローにしない。

## 目的

- 行動前に GitHub 上の対象を正確に特定する
- 要約、レビュー、変更の前に証拠を集める
- 異なる AI 実行環境でも再利用できる流れを保つ

## 入力

作業に必要な最小情報を集めるか、ローカル文脈から推定する。

- リポジトリ
- ブランチ、コミット、プルリクエスト、Issue の識別子
- 依頼された作業内容
- 利用可能な GitHub へのアクセス手段

必要な識別子が欠けている場合は、作業を進める前にユーザーへ確認するか、ローカル文脈から特定する。

## 手順

### 1. 対象を特定する

その作業が何を対象にしているかを明確にする。

- リポジトリまたはブランチ
- プルリクエスト
- Issue
- レビュースレッドまたはインラインコメント
- CI 実行、失敗したチェック、ワークフロージョブ

対象が曖昧なまま推測で進めない。

### 2. 作業種別を分類する

詳細を集める前に、主目的を一つ決める。

- 状況把握や要約
- レビュー指摘の整理
- CI 失敗調査
- GitHub 上の議論に対応するコード変更
- 公開、同期、ブランチ操作

一度に追う主目的は一つに絞る。

### 3. 証拠を集める

要約より一次情報を優先する。

- プルリクエスト本文、変更ファイル、レビューコメント、チェック結果
- Issue 本文と関連する議論
- ローカルの git diff、コミット履歴、関連ソースファイル
- CI ログや失敗出力

GitHub にアクセスできない場合はその事実を明示し、ローカルで実際に確認できる証拠だけを使う。

### 4. アクセス手段を選ぶ

現在の環境で使える最善の GitHub アクセス手段を選ぶ。

- GitHub ネイティブ連携があればそれを使う
- コマンドラインツールが使えるならそれを使う
- リモートアクセスが不要ならローカルの git 情報を使う
- 直接アクセスできない場合は、ユーザーが示した文脈を使う

どの環境にも同じツールがあると決めつけない。
アクセス不能を、断定的な推測で隠さない。

### 5. 証拠が十分な場合だけ行動する

変更前に次を確認する。

- 集めた証拠が依頼内容を裏付けているか
- その作業にリモート文脈、ローカル変更、または両方が必要か
- 関連する一次情報を読まずに、コメント解決、失敗の切り捨て、結論公表をしないか

ローカル変更が必要な場合は、あわせてブランチ方針も確認する。

- `main` 上で直接作業を始めない
- 現在のブランチが `main` なら、編集やコミットの前に作業内容に合うブランチを作る
- ユーザーが明示的に許可した場合のみ、`main` に留まって直接作業してよい

### 6. 追跡可能な形で報告する

要約や結論には、その根拠を辿れる情報を含める。

- 何を対象として確認したか
- 何が確認できたか
- 何を変更したか
- 何が未確定か

アクセスが部分的だった場合は、その制約を明示する。

## ガードレール

- リポジトリ、PR、Issue、ワークフローの詳細を捏造しない
- 一次情報があるのに、二次要約を正本扱いしない
- 認証、権限、接続性の問題を隠すフォールバックを加えない
- ユーザーが明示しない限り、無関係な GitHub 目的を一つの手順に混ぜない

## 出力要件

参照のみの作業では、次を返す。

- 特定した対象
- 主な要点または要約
- 不確実性やアクセス不足

変更を伴う作業では、次を返す。

- 特定した対象
- 変更を正当化する証拠
- 実施したローカルまたはリモート操作
- 残っているフォローアップ
