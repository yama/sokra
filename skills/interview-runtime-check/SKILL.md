# インタビュー実行確認

このスキルは、Sokra の会話インタビュー実装を AI 自走で確認するときに使う。
単なる API 疎通ではなく、開始導入、会話継続、終了条件、warning、fallback、会話の自然さまで確認対象にする。

## 目的

- 会話フローの破綻を早く見つける
- fallback や warning を通常成功に紛れ込ませない
- API ベース確認と実ブラウザ確認の差を意識して報告する

## 前提

- `AGENTS.md` のフォールバック方針に従う
- fallback は成功扱いではなく warning 扱いで見る
- 開始導入のように決定的に生成できる箇所は、通常経路が安定していることを優先する
- チェックポイントの通過順序は固定しない。直前の回答で自然に触れられた論点を記録し、次の返答だけを確認する
- チェックポイントは必達ノルマではなく観測点として扱う。自然に寄れなかった論点が残ることも有効な会話記録である
- 自由会話は Gemini の JSON 応答で発話生成する
- LLM 障害をフォールバック会話で延命しない。JSON パース失敗は 1 回だけ再試行し、失敗が続く場合は異常終了として扱う
- 通常会話の設計確認では `DESIGN.md` をプロンプト設計の正本として見る。`interview-flow.js` はチェックポイント状態と中断ガードを担当し、通常ターンの固定質問生成を持たない
- `difficulty` は独立した設問として必ず聞かない。参加者が面白さや便利さを話している流れで、こわさや違和感を前提にした質問をしない
- 参加者が具体例や面白がった理由を出したあと、相づちだけで会話が止まる場合は、8秒程度待った追加発話で自然に橋渡しできているかを見る

## 確認レベル

### 1. API ベース確認

まずは `http://127.0.0.1:3000` の API に対して自走確認する。
最低限、次を確認する。

- 開始導入が想定どおり始まる
- 通常ターンが自然に継続する
- 代表的なシナリオで終了条件まで到達する
- `warning` や `fallback` が出ていない
- 最終イベントが通常の `closing_message` であり、異常終了で畳まれていない

Playwright が使える環境なら、API ベース確認だけで終わらせず、ヘッドレスの UI 実行も優先する。

### 2. ログ確認

API ベース確認で異常が出たら、`data/sessions/*.jsonl` を見る。
次を優先して確認する。

- `ai_turn_error`
- `warning`
- `chat_fallback`
- `chat_recovery_prompt`
- `chat_failure_abort`
- `closing_message`

### 3. ヘッドレス UI 確認

Playwright が使える場合は、`npm run test:e2e` のようなヘッドレス確認を優先する。
古いローカルサーバーを再利用すると、分割後の静的ファイルや最新の会話制御が反映されないことがある。テストは原則として現行コードでサーバーを起動し直し、ポート競合が出たら古いプロセスを止めてから再実行する。
`reuseExistingServer: false` の前提を崩さず、古い `localhost` プロセスに誤接続していないことを確認する。
実行環境によっては sandbox が `127.0.0.1:3000` への listen を拒否することがある。その場合はコード不具合と決めつけず、権限を上げて同じテストを再実行して切り分ける。
次を必ず見る。

- ボタンフェーズから開始できるか
- 入力欄と送信ボタンが正常に動くか
- 会話終了時に `endedNote` が表示されるか
- 画面下部の `usageStats` に `fallback: 0回` が出ているか
- セッションIDを使って `data/sessions/*.jsonl` 相当の API を照合し、最終 AI イベントが `closing_message` か
- 通常シナリオで `/api/gemini` が呼ばれているか
- `/api/gemini` の応答が JSON として検証され、未知IDや完了済み checkpoint が無視されているか

通常経路では、Playwright の route interception で `/api/gemini` をモックし、呼び出し回数が 0 ではないことを確認する。
JSON パース失敗や API 失敗を確認するときだけ、route interception で意図的に不正応答やエラーを返す。偶発的な API 障害待ちにしない。
UI 上の見た目だけで合格にせず、代表シナリオごとにセッション API と照合して `warning: 0件` と最終 AI イベント種別を確認する。

### 4. 実ブラウザ確認

API ベースで問題がなくても、実ブラウザ確認は別物として扱う。
実ブラウザ確認をしていない場合は、未確認だと明示する。

## 最低限流すシナリオ

### シナリオ A: 標準

- 参加背景
- 温度感
- 印象点
- 自然に出てきた引っかかりや違和感
- 実務接点

主要な論点が自然に拾われ、`closing_message` で終わることを確認する。
`ended: true` だけで合格にせず、`chat_failure_abort` や warning に逃げていないことも確認する。

### シナリオ B: 低熱量

- 背景が弱い
- 温度感が低い
- 途中で短文が続く

無理に押し込まず進むか、自然に終わることを確認する。

### シナリオ C: 話題継続

- 特定製品名を含む話題
- 印象点から派生する短文

話題が途中で不自然に飛ばないことを確認する。

### シナリオ D: LLM応答検証と会話不成立

- `/api/gemini` が通常会話で呼ばれることを確認する
- 不正なJSON応答は1回だけ再試行されることを確認する
- ユーザーが短い話題提示をしたあと、同じ入口質問を繰り返さないことを確認する
- ユーザーが会話不成立を指摘したら、通常質問を続けず中断か終了へ移る

次を確認する。

- checkpoint 回収のために順番を固定していない
- 直前の回答を別 checkpoint に無理やり分類していない
- `difficulty` 回収のために、前向きな感想へこわさや違和感を差し込んでいない
- 自然に寄れなかった checkpoint を埋めるためだけに会話を引き延ばしていない
- 会話不成立の指摘が出たら、通常質問を続けず中断か終了へ移る

## 自然さの確認観点

終了まで通っただけでは十分ではない。
次も見る。

- 直前の質問に答えているのに、同じ入口質問を繰り返していないか
- 直前の話題を受けているか
- 具体例や面白がった理由が出たあと、相づちで受けたまま止まる場合に追加発話で自然に次の話題へ進めているか
- checkpoint 回収のために急に話題が飛んでいないか
- checkpoint の順序が固定された聞き取りに見えていないか
- checkpoint 未完了を不自然に埋めにいかず、想定外の感想としてログ価値を残せているか
- 面白い、便利そうという流れで「こわさはありましたか？」のような誘導質問をしていないか
- 直前のやり取りに対する回答として受けているか
- 締めが唐突すぎないか
- `大丈夫です` のような曖昧な緩衝句が通常ターンで乱発されていないか
- 聞くべき checkpoint が残ったまま、異常終了や中断文で畳まれていないか
- ユーザーが訂正した直後に、別の topic へ飛んでいないか
- ユーザーが「噛み合っていない」と言ったあとに、さらに通常質問を続けていないか
- 会話の自然さ判定を特定単語に依存させず、質問と回答の接続、topic 遷移、締めの妥当性で判断しているか

## warning / fallback の扱い

- `warning` が 1 件でも出たら「正常完了」とは言わない
- `fallback` が出たら、そのシナリオは要注意扱いにする
- 同じ fallback が繰り返されたら、会話品質の問題ではなく異常系として扱う
- `ended: true` でも、`chat_failure_abort` や `chat_recovery_prompt` を経由していれば通常完了と区別する
- `chat_recovery_prompt` は暫定回復であり、常用経路化していないかを確認する
- 正常系だけ通っていても、warning 経路を未確認なら十分とは言わない
- `closing_message` まで到達していても、途中に `warning` や `fallback` があればそのシナリオは不合格扱いにする

## 失敗時の切り分け順

1. `warning` / `fallback` / `ai_turn_error` の有無を見る
2. 最後の AI イベントが `closing_message` か `chat_failure_abort` かを分ける
3. 失敗が開始導入か通常ターンか終了条件かを分ける
4. 聞けていない checkpoint が残ったまま終わっていないかを見る
5. ユーザーの訂正や会話不成立指摘を、通常の内容回答として誤解していないかを見る
6. 直前のやり取りに対する回答として扱えているかを見る
7. モデル応答の問題か、JSON検証の問題か、checkpoint 反映の問題かを切る
8. 常用経路化した例外処理なら、フォールバック改善ではなく通常経路を直す
9. 通常ターンの固定質問生成が再び `interview-flow.js` や `app.js` に増えていないかを確認する

## 出力要件

報告では最低限、次を分けて書く。

- どのシナリオを流したか
- 終了まで到達したか
- `warning` / `fallback` の有無
- 最終終了種別が `closing_message` か異常終了か
- 会話の自然さに関する所見
- API ベース確認か、ヘッドレス UI 確認か、実ブラウザ確認か
- warning 経路を意図的に確認したか、それとも正常系だけか
