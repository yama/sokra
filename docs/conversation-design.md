# 会話設計メモ

## この文書の位置づけ

Sokra における会話設計の意図と、プロンプトで調整する領域、ロジックで担保する領域の境界を整理する。

この文書は会話設計の正本とし、実行時にモデルへ渡す最終的な指示文そのものは `src/prompt.js` を参照する。
AI が返す JSON 応答の契約は `docs/conversation-response-format.md` を参照する。
また、ターン分類やモード遷移の判定ロジックは `src/gemini.js` を参照する。

## 目的

- ゲストが構えずに話せる空気を作る
- 感想を整理させるより、断片的な記憶や感覚が出てくる余地を残す
- その場で解釈を確定せず、あとからホストが読み返せる記録を残す

## 非目的

- ゲストに深い自己理解や結論をその場で到達させること
- 分析や要約によって会話をきれいに整えること
- 取りこぼしを恐れて不自然な詰問を続けること

## 基本姿勢

- 聞き手は「引き出す人」より「話しやすい場を作る人」として振る舞う
- 通常会話では落ち着いた相づちを優先し、過度に盛り上げない
- 遊び入力や脱線は即座に矯正せず、短く付き合って流れを見る
- 自然に拾えなかった論点を埋めるためだけに会話を延命しない

この文書で強く定義するのは、聞き手の人格と責務分担である。
個々の言い回しや小さなテクニックは、ここで固定しすぎない。

## 聞き手の人格

この機能で最も重視するのは、質問技法より先に伝わる聞き手の人柄である。
`src/prompt.js` でも、この人格を会話ルールより先に置く。

- まず相手に合わせる
- 面白いことには明るく笑う
- ふざけや脱線にも感じ悪くならず、少し付き合う
- 言葉足らずでも急かさない
- 安心して気持ちがほぐれたところで、やんわり聞きたいことを聞く

細かいテクニックや局所ルールは、この人格を支えるための補助であり、正本ではない。

## 応答の構造

1 回のユーザー入力に対して、AI の応答ターンは次の要素で構成される。
詳細な JSON 契約は `docs/conversation-response-format.md` を参照する。

- `reactions`
  相づちや短い反応の配列。0件でもよい
- `question`
  次に相手へ投げる明示的な問い。必要なときだけ含める
- `checkpoints_filled`
  今回の発言で自然に拾えた論点
- `ready_to_close`
  会話を閉じる準備が整ったか

設計上、通常は `question` が進行を担い、`reactions` は受け止めを担う。
ただし、単発の短い遊び入力では `reactions` のみで返すターンを許容する。

## Gemini 呼び出しの実態

UI 上は 1 本のインタビューセッションとして続いて見えるが、Gemini API とのやり取り自体は stateful な会話セッションを維持していない。

各ターンでは、`src/gemini.js` がその時点の材料を毎回組み立て直して `POST /api/gemini` へ送る。
具体的には次を都度再構成する。

- その時点の `systemPrompt`
- 必要な会話履歴 (`conversationHistory`)
- 今回のユーザー入力 (`userText`)

サーバー側の `api/lib/gemini.php` は、その都度 `contents` を作って Gemini の `generateContent` を呼ぶ。
したがって実装の実態は「見た目は継続会話、API 呼び出しは毎ターン stateless に再構成」である。

この前提を理解しておくと、次の判断がしやすい。

- どこまでを履歴として渡すか
- system prompt に何を持たせるか
- 会話の継続感を prompt と履歴のどちらで支えるか
- セッション保存と LLM 呼び出しの責務をどう分けるか

## 会話モード

外部仕様として扱う会話モードは次の 3 つとする。

| モード | 概要 | `reactions` | `question` |
|---|---|---|---|
| `normal` | 通常の感想会話 | 自然なときのみ | 必要なときのみ |
| `playful` | 単発または連続した短い遊び入力 | 必須 | なし |
| `shiritori` | しりとりの流れが明確 | 必須 | なし |

### `normal`

通常の感想共有、質問への返答、やや短い雑談を扱う標準モード。

- `reactions` は、その発話でなければ成立しない具体性があるときだけ入れる
- どの会話にも使えそうな汎用相づちに寄りすぎない
- `question` は必要なときだけ返す
- 笑い相づちや絵文字は常用しない

### `playful`

単発のボケや、しりとり未満の遊び入力に対し、まず相手に合わせるモード。

- `question` は出さない
- まず相手が何をしてきたかを見る
- 必要以上に意味づけせず、軽く合わせる
- 遊びに付き合うか、笑って受けるか、少しだけ返すかは prompt 側で決める
- 真面目な受け答えや、本題への回収を急がない

このモードの中で、実装は `single` と `streak` を補助事実として持ってよいが、外部の主モードとしては増やさない。

### `shiritori`

短い遊び入力の連続が、しりとりとして成立していると判定できるときのモード。

- `reactions` は必須
- 基本は `reactions` に次の語を 1 語だけ返す
- `question` は出さない
- 返し方の基本形は短い一手だが、会話設計の主目的はしりとりそのものではない
- しりとりが続いている間は本題に引き戻さない
- しりとりが崩れても詰問しない

## モード判定の責務

モード分類の責務はロジック側に置く。
現在の判定は `src/gemini.js` の `buildTurnPolicy()` と関連関数が担う。

責務分担の原則は次の通り。

- ロジックが決めるのは事実だけにする
- prompt が決めるのは返し方にする

このとき、主軸は「文字列の種類」ではなく「発話の役割」に置く。
しりとりは、その役割認識の結果として見つかる一例であり、会話設計の主目的ではない。

ここでいう「事実」とは、たとえば次を指す。

- 短語遊びかどうか
- 何回続いているか
- しりとりとして成立しているか
- 直近にどんな短い入力が続いているか
- 直近に AI がどんな短い返しをしたか

ここでいう「返し方」とは、たとえば次を指す。

- 軽く笑うか
- ひとこと乗るか
- しりとりの次の語を返すか

ロジックが早い段階で返し方まで決めすぎると、不自然な固定化が起きやすい。
特に遊び入力では、回数や文字種だけで返答文体まで決め打ちせず、ロジックは補助信号に留め、返し方は prompt 側で調整する。

また、`絵文字ひとつで返す`、`オウム返しを避ける` などの細則は、自然さを壊しやすい場面での補助ガイドとして扱う。
人格と会話姿勢が十分に機能しているなら、これらを絶対ルールとして強制しない。

現時点の方針は次の通り。

1. まず、短い単語ボケかどうかを判定する
2. その連続がしりとりとして成立していれば `shiritori`
3. それ以外の短い遊び入力なら `playful`
4. それ以外は `normal`

ここでいう「どこまでを短い入力とみなすか」「何回続いたら単発扱いから連続扱いへ寄せるか」はロジック側の責務であり、この文書では仕様意図だけを定義する。

## 優先順位

同一ターンで複数のルールが衝突しうる場合、優先順位は次の通りとする。

1. 出力形式の制約
2. クロージング中かどうか
3. 遊び入力モード固有のルール
4. 通常の相づちルール
5. 論点回収や話題転換のガイド

特に `playful` と `shiritori` は、そのターンでは通常の相づちルールより優先する。

## プロンプトで調整する領域

次は、原則として `src/prompt.js` の調整で扱う。

- 聞き手の人柄
- まず相手に合わせる姿勢
- 相づちの文体と温度感
- 笑い方、驚き方、軽く乗るときの語感
- 遊び入力のときにどこまで説明を抑えるか
- 通常会話へ戻すときの橋渡し表現
- クロージング前置きの言い回し
- 論点回収を露骨にしないための誘導表現

ここでは、細かい禁止事項を積み増すより、人格と優先順位が自然に伝わる記述を優先する。

## ロジックで担保する領域

次は、原則としてコード側で扱う。

- 会話モードの分類条件
- モード遷移の閾値
- `reactions` のみを許容するターンかどうか
- `reactions` のみターン後に待機するか、自動フォローするか
- クロージング遷移や自動フォローの発火条件

会話の振る舞いを変えたいときは、まずプロンプトだけで目的を達成できるかを検討し、分類や制御の変更が必要な場合だけロジックを触る。

## 変更判断の目安

### プロンプトだけで済ませるべき変更

- 相づちが固いので柔らかくしたい
- 遊び入力に対して少し笑う方向へ寄せたい
- 質問が詰問調に見えるので弱めたい
- クロージングを少し自然にしたい

### ロジック変更を検討すべき変更

- 単発判定の長さ条件を変えたい
- 2 回連続ではなく 3 回連続でモードを切り替えたい
- しりとり判定を別条件へ変えたい
- `reactions` のみ応答のあとに常に追加質問したい

## 期待する保守方針

- 会話設計の意図はこの文書で整理する
- 実装はこの文書を参照しつつ、`src/prompt.js` と `src/gemini.js` に分担して落とす
- 文言調整の理由をコードコメントへ増やしすぎず、この文書に寄せる
- 新しいモードを追加する前に、既存 3 モードと補助事実の調整で吸収できないかを検討する

## 現時点の未整理点

- 通常モード内での `reactions` 省略基準を、さらに例示した方がよいか
- 遊び入力から通常会話へ戻すタイミングを、設計意図としてもう少し言語化するか
- 自動フォローと会話モードの相互作用を、この文書にどこまで含めるか
